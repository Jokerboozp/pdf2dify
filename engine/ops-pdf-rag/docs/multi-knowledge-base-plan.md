# 多知识库实施方案

2026-09-16。目标环境：自部署 Dify 1.17.1。本文保留初期扩展设计；九个主题库与单库/双库路由现已实际创建，257份来源已全部本地处理，全部当前文档索引与远端完整性核查已完成，验收记录见 acceptance.md。当前实现及剩余事项以 [全量图文演示说明](full-demo.md) 为准，以下“建议/后续”不是已完成承诺。

## 结论与依据

采用一个用户入口、按业务主题组织知识库、按问题选择检索范围的结构。当前清点为 257 份 PDF、5,244 页。拆库用于减少相似术语造成的串答、便于版本和业务维护；PDF 数量本身不是判断一个库是否过大的充分依据。

以下分类依据本地 `data/inventory.json` 的目录，不代表内容和业务时效已审定。ERP 运维资料目录有 250 份 PDF，培训目录另有 7 份。建议先规划 9 个主题库，随模块处理进度创建，不一次全部导入。

| --- | --- | --- |
| 财务核算 | 核算模块 22 份 | 财务常见问题按条目归属分配，核算条目进入本库 |
| 资金与预算 | 资金 14 份、预算 3 份 | 接收财务常见问题中属于本域的条目 |
| 采购与物资 | 物资管理 44 份 | 3 份物资采购培训按流程整理后进入本库 |

培训资料不是独立业务域，不单独建“培训库”。一份综合 PDF 可以按章节生成多个入库文档；同一知识条目默认只有一个主归属，跨域通过联合检索引用，避免复制后更新不一致。

9 个主题库是初始组织方案，不是平台限制或最终固定数量。同一主题内若长流程与短 FAQ 确实需要不同的分段模式，可以增设流程库；先根据检索结果证明需要，再细分。

## 用户问答与 Dify 编排

流程：用户提问 → 结合对话整理完整问题 → 判断业务对象、动作和模块 → 不明确则追问 → 进入对应检索分支 → 筛选匹配证据 → 返回步骤、原文图片及文件页码。

在现有 Chatflow 上增加结构化分类与条件分支。每个分支的知识检索节点预先绑定主题库；不假定知识检索节点能接受模型临时生成的知识库 ID。保留现有不依赖代码沙箱的实现方式。

- 通常选择 1 个主题；明确跨域时选择预配置的 2 个相关主题，例如项目与核算、采购与主数据操作。
- “物料编码规则是什么”主要查询主数据标准；“如何新建物料”主要查询主数据操作，必要时补充采购资料。
- “结转如何撤销”不能仅凭“结转”就选某个流程，应先明确项目结转、维修订单或其他业务对象。事务码和历史对话作为判断依据，不能覆盖当前提问的明确条件。
- 检索不到时先核对模块或引导补充报错、事务码、项目类型；不自动搜遍全部知识库再拼凑答案。
- 不在一个检索节点中默认勾选全部主题库。Dify 官方说明：多库被选中时会全部检索，然后合并结果；这本身不等于按问题路由。
- 后续重排模型属于可选优化。当前实例没有配置可用重排模型，不能把它写成已经实现的能力；先用已有混合检索建立基线。

## 入库单位与图文绑定

清洗后的入库单位为一个完整故障处理条目，或一个有前置条件、步骤和验证结果的操作流程。长流程保留完整父级内容，再划分子段，避免只检索到中间一步。

建议文档元数据：`domain`、`subdomain`、`procedure_type`、`project_type`、`system_version`、`review_status`、`validity_status`、`source_id`、`source_hash`。来源文件、起止页、适用条件与图片关系同时写入可检索正文和本地清单。

Dify 元数据主要作用于文档，因此不同模块、版本或适用条件的条目不能继续集中打包为同一入库文档，再期望用文档字段精确过滤其中某一条。扩展阶段按单个流程或元数据一致的小组生成导入文件。

每个流程携带原 PDF 对应截图、截图所在页及稳定标识。复用已验证的 Dify 图文导入方式，先用一个新增模块验证拆分文档后的图片关联；不把图片单独建成脱离步骤的知识库。PDF 解析、OCR 和图片筛除留在本地；云端模型使用获准的文本，回答通过图片链接展示原始截图。

版本不明的资料标记 unknown，业务复核状态保留 pending，不因文件名或导入时间较新就视为现行版本。新旧版本按适用版本选取；发生冲突时说明来源或追问，不把冲突步骤合并。

如果不同岗位存在访问边界，应由可信身份和应用后端限定可检索的库。模型分类和用户自行填写的岗位不是权限控制。

## 分批实施与验收

1. 保留现有 44 条图文试点和当前工作流。先建立全量分类清单，每个来源记录建议主题、判定依据及待复核状态；不以目录推断替代内容复核。
2. 先接入财务核算、项目管理、采购物资三个业务主题。只处理代表性完整流程，验证正确选库和跨库组合，再逐批扩展覆盖范围。
3. 建立包含同词不同模块、跨模块、问法不明确、资料未覆盖、新旧版本、图片归属的测试集。分别检查选库是否正确、是否召回正确流程、步骤是否完整、图片和页码是否一致。
4. 针对失败原因调整分类、字段、流程边界或检索设置。现有离线 FAQ 命中率不作为多库验收结果；使用真实业务问题并由业务人员复核。
5. 扩展到其余主题。通过来源 SHA 和条目稳定 ID 只处理变更文件；新内容检查通过后再替换旧内容，保留可回退映射。增量 API 同步仍需本机配置 Dify API 凭据及目标实例实测。

当前已实现：全量清点及原生文字提取、局部本地 OCR、44 条图文问答试点。未实现：本方案的多库拆分、模块路由、全量业务复核与多库验收。本文未修改线上知识库和 Chatflow。
